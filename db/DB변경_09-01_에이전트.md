## 1. 실행 — 기존 절차 뒤에 이어 붙인다

```bash
# db/README_시드적재.md 의 ①~⑪ 을 먼저 끝낸 상태에서
MYSQL="/c/Program Files/MySQL/MySQL Server 8.0/bin/mysql.exe"
OPTS="--force --default-character-set=utf8mb4"
DB="-h127.0.0.1 -P3307 -uroot -p storeflow_db"

# ⑫ 엔티티↔DB 격차 — 컬럼 3 + 테이블 1
"$MYSQL" $OPTS $DB < db/seed/05_backend_gaps.sql
# ⑬ 채팅 첨부 테이블 (jmy 님 제공 파일)
"$MYSQL" $OPTS $DB < db/Chat_attachment.sql
# ⑭ 로그인 계정 ↔ 세계 회원 다리
"$MYSQL" $OPTS $DB < db/seed/04_demo_accounts.sql
# ⑮ 구매 이력을 화면 장부(orders)에도 투영  ⚠ ⑭ 뒤여야 한다
"$MYSQL" $OPTS $DB < db/seed/06_demo_orders.sql
```

⚠ **옵션 둘은 선택이 아니다** — `--force`(중복 오류에서 안 멈춤) ·
`--default-character-set=utf8mb4`(윈도우 클라이언트 기본이 euckr 이라 한글이
깨진다). 기존 절차서 §2-⑧·⑨ 와 같은 이유.

⚠ **⑮ 는 ⑭ 뒤여야 한다.** ⑮ 가 ⑭ 가 만든 데이터를 읽어 투영한다.

### 검산 — "돌렸다"와 "됐다"는 다르다

`--force` 는 오류를 넘기므로 반드시 확인한다.

```bash
"$MYSQL" $OPTS $DB -e "
SELECT 'members'        t, COUNT(*) n FROM members         WHERE member_id>=10000000
UNION ALL SELECT 'purchases',       COUNT(*) FROM purchases       WHERE member_id>=10000000
UNION ALL SELECT 'wishlists',       COUNT(*) FROM wishlists       WHERE member_id>=10000000
UNION ALL SELECT 'orders(1~30)',    COUNT(*) FROM orders          WHERE consumer_id BETWEEN 1 AND 30;
SHOW COLUMNS FROM consumer LIKE 'point%';"
```

기대값(09-01 실측):

```
members       30        purchases   1991
wishlists    154        orders       181   (기존 1건 포함)
consumer 에 point_balance · point_earned_total 두 줄
```

## 2. 무엇이 바뀌나 — 파일별

### ⑫ `db/seed/05_backend_gaps.sql` — 엔티티에는 있는데 DB 에 없던 것

JPA 엔티티 24개를 `information_schema` 와 **전수 대조**해서 찾았다.
`ddl-auto: none` 이라 Hibernate 가 안 만들어 주므로, 없으면 그 도메인을
건드리는 순간 500 이 난다.

| 무엇 | 어디에 | 없으면 |
|---|---|---|
| `point_balance` `point_earned_total` | `consumer` 에 컬럼 추가 | **로그인·회원가입이 전부 500** |
| `points_used` `points_earned` | `orders` 에 컬럼 추가 | 주문 저장 자체가 500 |
| `shopping_date` | `cart_group` 에 컬럼 추가 | 장보기 리스트의 "장 볼 날짜" |
| `point_transaction` | 테이블 신설 | 포인트 적립/사용 |

⚠ **`shopping_date` 는 새로 만든 게 아니다.** `db/Migration_guest_cart_v1.sql`
**64행에 이미 있는데 그 파일이 끝까지 안 돌았다.** 08-28 에 채팅 도메인이
통째로 500 이던 것과 같은 사고다(절차서 §2-⑦).

⚠ **정식 DDL 은 백엔드 담당 몫이다.** 위 넷은 **엔티티에서 역산한 판**이라
타입·길이는 맞지만 인덱스·외래키는 최소한만 걸었다. 팀 스크립트가 오면
그것으로 갈아탄다.

### ⑬ `db/Chat_attachment.sql` — 채팅 첨부 테이블

jmy 님이 `344c273` 과 함께 주신 파일. 파일 머리에도 *"ddl-auto: none 이라
직접 실행 필요"* 라고 적혀 있다. 없으면 채팅에 사진·파일을 붙일 때 500.

### ⑭ `db/seed/04_demo_accounts.sql` — 로그인 계정에 이력을 붙인다

**문제**: 백엔드는 로그인한 손님의 이력을 `member_id = 10,000,000 +
consumer_id` 로 찾는다(`Member.toMemberId`). 그런데

```
세계 시드 회원        1001 ~ 11000
데모 슬라이스 이력    1001 ~ 1030 에만
10,000,00x 대역        구매 0건
```

⇒ **어떤 계정으로 로그인해도 이력이 0건**이었다. 그런데 창구는 `200 []` 를
돌려주므로 **오류가 아니다** — AI 는 "이력이 없는 손님"으로 알고 그럴듯하게
답한다. 화면은 멀쩡한데 개인화만 죽어 있는, 제일 늦게 발견되는 종류다.

**무엇을 하나**: 시드 회원 1001~1030 의 **구매·찜·행동 이벤트를
10,000,001~030 으로 복사**한다(옮기지 않는다 — 원본은 학습·분석 재료다).

```
로그인 계정   01080000001 ~ 01080000030   /   비밀번호 test1234
              (consumer_id 1~30  →  member 10,000,001~030)
```

**왜 코드가 아니라 데이터로 고쳤나**: `Member.toMemberId` 의 오프셋을 데모용
으로 바꾸면 한 줄이면 되지만, 그건 **저장소의 계약을 내 기계에서만 거짓으로
만드는 것**이다. 다른 브랜치·다른 기계에서 띄우면 그대로 깨진다. 데이터로
놓으면 계약이 참인 채로 어디서든 같은 결과가 나온다.

### ⑮ `db/seed/06_demo_orders.sql` — 구매 이력을 화면 장부에도

**문제**: 구매 장부가 둘인데 서로 겹치지 않았다.

```
purchases            48건   ← AI 에이전트가 읽는 곳 (세계 시드)
orders / order_item   1건   ← 화면(마이페이지 구매내역)이 읽는 곳
```

로그인해서 구매내역을 열면 비어 있는데 AI 는 그 이력으로 취향을 말한다.
`GET /api/orders/frequent` 가 `[]` 를 돌려주던 이유다.

**무엇을 하나**: 같은 장바구니(`basket_id`)를 **한 주문으로 묶어** `orders` +
`order_item` 으로 투영한다. 적립 2%·등급 문턱은 `Grade` 규칙 그대로 계산하고,
**`consumer` 의 누적 포인트·등급도 같이 맞춘다** — 주문만 넣고 포인트를 안
맞추면 "구매는 많은데 등급이 베이직"이라는 자기모순 화면이 된다.

방향이 반대면 안 된다: `orders → purchases` 로 가면 AI 가 읽을 이력이 1건뿐
이라 개인화가 도로 죽는다. **세계가 만든 이력이 원본이고 화면 장부는 그것의
투영**이다.

## 4. 되돌리기

전부 **추가**만 했고 기존 데이터는 안 건드렸다. 되돌릴 때는 넣은 것만 지운다.

```sql
DELETE oi FROM order_item oi JOIN orders o ON o.order_id = oi.order_id
  WHERE o.consumer_id BETWEEN 1 AND 30 AND o.order_id > 1;
DELETE FROM orders          WHERE consumer_id BETWEEN 1 AND 30 AND order_id > 1;
DELETE FROM purchases       WHERE member_id >= 10000000;
DELETE FROM wishlists       WHERE member_id >= 10000000;
DELETE FROM consumer_events WHERE member_id >= 10000000;
DELETE FROM members         WHERE member_id >= 10000000;
```

⑫⑬ 의 컬럼·테이블은 **되돌리지 않는다** — 엔티티가 요구하는 것이라 지우면
다시 500 이 된다.

⚠ **세계 시드를 다시 적재하면 ⑭⑮ 도 다시 돌려야 한다.** 재적재가
`10,000,00x` 대역을 지우기 때문이다. 절차서의 마지막 단계로 기억한다.

## 5. 곁 — 백엔드가 안 뜨는 다른 이유 하나 (DB 아님)

DB 를 다 맞췄는데도 백엔드가 안 뜨면 `application.yml` 을 본다.
`344c273` 의 `ObjectStorageConfig` 가 키 다섯을 요구한다. 이 파일은 git
미추적이라 각자 채워야 한다 — 기존 `ncp:` 블록에 `sms:` 와 **같은 깊이**로:

```yaml
ncp:
  sms: { ... 기존 그대로 ... }
  object-storage:
    endpoint: https://kr.object.ncloudstorage.com
    region: kr-standard
    access-key: dummy
    secret-key: dummy
    bucket: dummy-bucket
```

더미 값으로도 뜬다(`S3Client` 객체만 만들고 접속은 업로드할 때만 한다).
⚠ 들여쓰기가 핵심 — `sms` **안**에 넣으면 `ncp.sms.object-storage` 가 되어
같은 오류가 난다.
